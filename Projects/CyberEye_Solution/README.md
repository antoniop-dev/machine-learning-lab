# CyberEye Solutions — Synthetic Data Augmentation for Image Recognition

Proof of concept for a single question:

> **Does training data generated by a captioning → paraphrasing → diffusion pipeline actually improve a downstream image classifier, or does it just add noise?**

CyberEye Solutions' real problem is recognising equipment in critical-infrastructure imagery, where labelled photographs are scarce and expensive. That data cannot be used to prototype on, so the pipeline is built and measured on **Oxford-IIIT Pet** (37 breeds, 7 349 images) as a stand-in: a fine-grained classification task with the same shape as the real one — many visually similar classes, limited images per class.

The answer is delivered as a controlled experiment. Three classifiers, identical in every respect except their training set, scored on one untouched test split.

---

## The pipeline

| Stage | Notebook | Model | What it does |
|---|---|---|---|
| 1. Dataset acquisition | `01_DataAcquisition.ipynb` | — | Downloads Oxford-IIIT Pet, inspects it, builds a fixed stratified train/val split, persists the indices |
| 2.1 Captioning | `02_Captioning.ipynb` | `Salesforce/blip-image-captioning-base` | One caption per training image |
| 2.2 Caption QA | `02_Captioning.ipynb` | `openai/clip-vit-base-patch32` | CLIPScore + repetition-loop detection; weak captions retried with tuned decoding, then escalated to `blip-image-captioning-large`; the unsalvageable are dropped |
| 2.3 Breed injection | `02_Captioning.ipynb` | — | Rewrites the species word ("cat"/"dog") into the actual breed, so the caption carries the label |
| 3.1 Paraphrasing | `03_Rephrasing.ipynb` | `humarin/chatgpt_paraphraser_on_T5_base` | 2 reworded variants per caption |
| 3.2 Variant scoring | `03_Rephrasing.ipynb` | — | BLEU + ROUGE-L of each variant against its source caption |
| 3.3 Variant selection | `03_Rephrasing.ipynb` | `openai/clip-vit-base-patch32` | Picks the variant with the best CLIPScore against the *original image* |
| 4.1 Image generation | `04_ImageGeneration.ipynb` | `stabilityai/sd-turbo` | img2img: original image as init, selected variant as prompt |
| 4.2 Image QA | `04_ImageGeneration.ipynb` | `openai/clip-vit-base-patch32` | Scores each synthetic image against its class name and its prompt, against a per-class real-image baseline; flagged images are excluded |
| 5. Training | `05_ClassifierTraining.ipynb` | ResNet18 (ImageNet, frozen backbone) | Three runs — baseline, augmented, augmented-filtered |
| 6. Evaluation | `06_Evaluation&Comparison.ipynb` | — | Accuracy / precision / recall / F1, macro and per class, plus the comparison table |

Two quality gates sit in the pipeline for a reason: a caption that describes the wrong thing produces a synthetic image that teaches the wrong thing, and neither the caption gate (2.2) nor manual inspection can catch an img2img output where diffusion overwrote the class-relevant features. 4.2 exists to catch exactly that failure, and the third training run is what measures whether catching it was worth the images it costs.

---

## Why three runs, not two

| Run | Training data | Checkpoint |
|---|---|---|
| `baseline` | real training images only | `checkpoints/baseline_resnet18.pt` |
| `augmented` | real + **all** synthetic images | `checkpoints/augmented_resnet18.pt` |
| `augmented_filtered` | real + **CLIP-filtered** synthetic images | `checkpoints/augmented_filtered_resnet18.pt` |

`baseline` vs `augmented` answers *did synthetic data help?* `augmented` vs `augmented_filtered` answers *was the quality filter worth it?* — a question the first comparison cannot separate out.

Everything else is pinned so the training data is the only variable:

- same frozen ImageNet ResNet18 backbone, same freshly initialised 37-way head
- same seed (`42`), reapplied immediately before model init, so all three runs start from identical head weights and identical shuffling
- same hyperparameters, same deterministic transform, **no random augmentation anywhere**
- same validation split (real images only — synthetic images never leave the training half)
- same held-out test split, which no pipeline stage has seen

## Setup

Python 3.11. Tested with torch 2.12, torchvision 0.27, transformers 5.14, diffusers 0.39.

```bash
python3 -m venv .venv && source .venv/bin/activate
pip install torch torchvision transformers diffusers accelerate sentencepiece \
            scikit-learn pandas numpy matplotlib tqdm pillow \
            nltk rouge-score jupyter
```

`sentencepiece` is required by the T5 paraphraser's tokenizer, `accelerate` by the diffusers pipeline, and `nltk` + `rouge-score` by the 3.2 caption metrics.

The dataset is **not** downloaded automatically by notebooks `02`–`06`; they all open it with `download=False`. `01_DataAcquisition.ipynb` is the single place that fetches it (~1.6 GB in `data/` once extracted), so it must be run first on a clean checkout.

## Running the pipeline

```bash
jupyter notebook
```

Run the notebooks in order — `01 → 02 → 03 → 04 → 05 → 06`. Each one assumes its predecessors have run and left their artifacts on disk, and loads them rather than recomputing:

| Notebook | Reads | Writes |
|---|---|---|
| `01` | *(downloads the dataset)* | `data/`, `splits/train_val_indices.json` |
| `02` | `splits/train_val_indices.json` | `manifests/captions*.csv`, `manifests/paraphrase_input.csv` |
| `03` | `manifests/paraphrase_input.csv` | `manifests/caption_variants*.csv` |
| `04` | `splits/train_val_indices.json`, `manifests/caption_variants_selected.csv` | `data/synthetic/**`, `manifests/synthetic_images*.csv`, `manifests/augmented_train_index*.csv`, `reports/real_vs_synthetic_clip_report.csv` |
| `05` | `splits/train_val_indices.json`, `manifests/augmented_train_index*.csv` | `checkpoints/*_resnet18.pt`, `reports/*_history.csv`, `reports/training_histories.csv`, `reports/learning_curves.png` |
| `06` | `checkpoints/*_resnet18.pt`, `reports/training_histories.csv` | `reports/test_predictions_*.csv`, `reports/per_class_metrics.csv`, `reports/model_comparison.csv`, `reports/model_comparison.png` |

A missing upstream artifact raises an error naming the notebook that produces it, rather than a bare `FileNotFoundError`.

### Everything expensive is cached

Every stage that costs a model download or a GPU pass checks for its output on disk first and skips the work if it is already there — captioning, caption QA, paraphrasing, variant scoring, image generation, image QA, each training run, and each evaluation inference pass. Reruns after a kernel restart are cheap, and the model weights themselves are not even downloaded when their outputs are already cached.

**To force a stage to recompute, delete its output file(s)** from `manifests/`, `checkpoints/` or `reports/` and re-run the notebook.

## Configuration

The knobs worth knowing, all defined as constants at the top of their section:

| Constant | Notebook | Default | Meaning |
|---|---|---|---|
| `SEED` | all | `42` | Global seed; identical across notebooks |
| `VAL_SIZE` | `01` | `0.2` | Validation fraction of the trainval split |
| `CAPTIONING_LIMIT` | `02` | `200` | Images captioned — **local prototyping cap**, set to `None` for a full run |
| `CLIP_SCORE_THRESHOLD` | `02`, `03`, `04` | `0.7` | CLIPScore below which a caption is flagged |
| `NUM_VARIANTS` | `03` | `2` | Paraphrased variants per caption |
| `IMG_GEN_LIMIT` | `04` | `40` | Synthetic images generated — **local prototyping cap**, set to `None` for a full run |
| `CLIP_STD_THRESHOLD` | `04` | `1.5` | Std devs below the per-class real baseline before a synthetic image is flagged |
| `TRAIN_EPOCHS` | `05` | `15` | Maximum epochs; early stopping usually ends runs sooner |
| `EARLY_STOPPING_PATIENCE` | `05` | `3` | Flat validation epochs tolerated before stopping |
| `BATCH_SIZE`, `LEARNING_RATE` | `05` | `32`, `1e-3` | Shared by all three runs |

`CAPTIONING_LIMIT` and `IMG_GEN_LIMIT` are the two that matter most: at their defaults the pipeline runs end-to-end on a laptop in minutes, on a few hundred images. **Both must be raised (to `None`) for the experiment's results to mean anything** — a couple of dozen synthetic images cannot measurably move a 2 944-image training set.

## Hardware

`get_device()` picks CUDA → Apple MPS → CPU, so the same notebooks run unchanged on a laptop and on Colab. The intended workflow is to validate each stage locally at the default caps (MacBook Air M2, `mps`), then run the full pipeline uncapped on Colab (T4/A100), where SD-Turbo generation and the three training runs are the dominant costs.

## Results

**Not yet available.** The pipeline is implemented end to end and each stage has been run or verified, but the full uncapped run that would produce meaningful numbers has not been completed. `06` builds the comparison table and chart from whatever checkpoints are present; the written discussion — did augmentation help, which breeds benefited, where does it fall short — is deliberately deferred until the full-scale artifacts exist.

What `06` will report, per run: accuracy, plus precision / recall / F1 as both macro (every breed weighted equally — the honest read on whether augmentation helped the *weak* classes) and weighted averages, plus per-breed metrics in `reports/per_class_metrics.csv` for the class-level analysis.
